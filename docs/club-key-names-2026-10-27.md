It uses the existing governor identity and fixed checked mainnet mapping, independently verifies the owner's public-key signature, verifies the pinned running canister module/sole governor controller, submits only `approve_private_name_conversion`, then checks a consensus receipt digest covering the entire signed body and signature. It never begins a window, changes names, advances a conversion, deploys, signs, or releases locks.

The original artifact is `private-name-approvals/<plan-hash>.json`; generation is a decimal string, principals canonical text, byte fields numeric arrays, and signature lowercase hex. This is **not** the older `private-name-signed-approval-v1` JSON envelope: that signature cannot be translated or re-signed by delivery. The approval signer must produce the backend's exact versioned length-prefixed bytes (`admissionBytes`), explicitly bound to the original window generation and encrypted rows. No signing credential is used by the delivery workflow.

Remote delivery receipts are keyed by plan hash, bind the exact file/commit/event/operator/key/module, and retain an unknown intent before the single submission. Git commits parent the observed receipt-branch head and update it non-force; races or failed acknowledgements stop. Every successful checkpoint is read back at its acknowledged commit and must remain the branch head before submission. Branch protection must enforce administrators and prohibit force pushes/deletion. Reconcile accepts only an exact retained canister receipt; absence never permits unknown resubmission. Protected environment/source restrictions and external management exclusion remain required, not proven by workflow YAML.

**Activation prerequisites (not configured or approved here):** a private repository; the separate `private-name-approval-delivery` environment with Paul as required reviewer, prevent self-review, approved-branch-only deployments and protected workflow/source; an existing append-only receipt branch; the original human-signed exact-row artifact; and environment pins `PRIVATE_NAME_APPROVAL_DELIVERY_REPOSITORY`, `PRIVATE_NAME_APPROVAL_DELIVERY_SOURCE_REF`, `PRIVATE_NAME_APPROVAL_DELIVERY_SOURCE_COMMIT`, `PRIVATE_NAME_APPROVAL_RECEIPTS_BRANCH`, `PRIVATE_NAME_APPROVER_PUBLIC_KEY`, `IDENTITY_ACCESS_CANISTER`, `IDENTITY_APPROVAL_MODULE_HASH`. Set `PRIVATE_NAME_APPROVAL_DELIVERY_PROTECTION_READY=yes` only after verifying those protections. Reuse the existing `DEPLOYER_PEM` secret without replacing it. The backend receipt endpoint and original matching signer still require a separately approved deployment; rehearsal gates have not been relaxed and the mainnet workflow has not been run.

Local tests verify signature/artifact substitution, wrong targets/windows, persistence-before-submission, lost reply reconciliation, missing unknown outcomes and ingress bounds. Real two-group acceptance additionally submits through the same delivery core, loses the committed approval reply, verifies the backend signed-body receipt and reconciles without submitting twice. This tests real transport contracts, not Paul’s production signature or GitHub protection configuration.

## Privacy and cost limitations

A device that receives a shared key can retain it indefinitely; a 30-day cache expiry or application permission check cannot revoke a copied key or previously received ciphertext. Future cryptographic revocation requires a new key generation and re-encryption. Rotation is not implemented in this local batch. Current checks stop new unauthorized application disclosures, not access to material already obtained.

Shared keys must therefore never cover restricted names or personal emails. Savings are prospective: one key per original PII/club/device cache lifetime for club-replica reads, not one universal derivation for every user or every audience. Actual costs and cold-load timing are unmeasured.
