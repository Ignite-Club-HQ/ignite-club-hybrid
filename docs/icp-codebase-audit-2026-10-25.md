# Codebase-wide ICP dependency audit — 25 October 2026

## Verdict

**The identified application-state gaps are now implemented locally, including PlayHQ association linking.** The findings below describe the original audit evidence, not the current repaired line numbers; this is not a certification of every deployed feature.

Local changes cover member search, sponsor references, AI settings, legal refresh, GIF configuration, recap identity, board attachment discovery, team reward reports, goalkeeper counts, versioned feedback, durable fixture row receipts and complete administrative inventories. Restored II sessions and ICP-hosted/explicit ICP startup use on-chain configuration; an ICP session with missing services now refuses rather than using Supabase. General signed-out hybrid-origin bootstrap intentionally retains country-routing configuration precedence.

Association PlayHQ linking now creates the public competition and durable club/tenant/grade/sport record atomically on the owning competition canister. Repeated tuples return the same competition; sport changes conflict. Listing and sync use the owning group, sync rejects source mismatch and rechecks the binding after external awaits, and exact links survive upgrades and scoped snapshot round trips and are removed by authorized purge. Supabase PlayHQ behavior is preserved. The source PlayHQ service itself remains external; successful external feed delivery is not verified by a local link test.

Additional verification: the competition migration compiles; two disposable group canisters passed authorization, tuple deduplication, immutable-sport refusal, wrong-source sync refusal, memory-preserving upgrade, snapshot and purge checks. Focused repository/link parsing tests cover exact owning-club calls. Deploy using **Upgrade backend (all mainnet groups)** scope **history**, action **check** then protected **upgrade** with the checked hash; release the app afterward. No live upgrades or signed-in live acceptance occurred. Resend and Drive remain deferred.

Verification: 13 focused files / 86 tests pass in each backend mode; ICP guards and 17-contract drift pass. The public preview opened /auth with zero page errors; no signed-in Internet Identity session was available, so real-use acceptance remains unverified. No mainnet upgrade, credential change, email activation or repository transfer occurred.

## C. Related correctness findings — not off-chain storage

1. **Rewards reports ignore the chosen team and lose display identities.** `frontend/src/pages/ClubRewardsReportPage.tsx:285–309` explicitly ignores team filtering and maps reward/child/profile joins to null, while the selector remains available. `:318` aggregates distinct rewards under “Unknown Reward.” Use authorized team membership and stable reward IDs/names; resolve allowed recipient labels.
2. **Goalkeeper matches can be counted twice.** `frontend/src/components/reports/playerStatsReportExtras.ts:205–206` initializes both played/appointed counts from `goalkeeper_count`, then `:224–226` increments played matches again from detailed positions. Deduplicate by player/event and distinguish appointment from participation.
3. **CSV fixture import can partially commit but report only failure.** `frontend/src/components/FixturesCSVImport.tsx:724–731` creates events sequentially; success clears the form only after all rows, while `:747–750` reports generic failure. Earlier rows can remain committed. Existing duplicate checks mitigate retries but do not supply committed/failed/unknown per-row results; preserve those distinctions without replaying uncertain writes.
4. **AI admin “All Pro clubs” can omit groups/subscriptions.** `frontend/src/pages/AdminAICatchUpPage.tsx:139` uses `everyGroup` without `requireComplete`; `frontend/src/live/groupDispatch.ts:217–233` can merge successful groups only. `frontend/src/live/features/proAccess.ts:84–90` also turns individual subscription failures into null, and the admin skips missing subscriptions at `AdminAICatchUpPage.tsx:123–124`. “Enable all” uses this filtered inventory. Require complete administrative discovery and strict subscription reads; adding only `requireComplete` is insufficient.
5. **Photo-reminder Run now can conceal partial group execution.** `frontend/src/pages/AdminChatPhotoRemindersPage.tsx:145–158` runs mutations inside an `everyGroup` read aggregation without complete inventory or write outcome tracking; `:165–166` reports Done from surviving results. Enumerate complete messaging contexts first, then record explicit per-group outcomes. Do not blindly repeat successful or uncertain runs. An on-chain hourly timer does exist at `backend/messaging_domain/src/main.mo:1223–1226`; its live execution/settings in every group remain unverified, not a missing scheduler claim.
6. **Feedback title/description are reversed on admin readback.** `frontend/src/components/FeedbackDialog.tsx:61–66` sends the description as optional title and entered title as message; `frontend/src/live/features/insights.ts:310–320` forwards them unchanged; `frontend/src/pages/ManageFeedbackPage.tsx:112–119` renders the opposite interpretation. Adopt one consistent field contract and deliberate handling of existing records; do not blindly rewrite historical feedback.

## D. Strict isolation/configuration boundaries

- **Fresh/pre-auth startup still reads Supabase configuration.** `frontend/src/App.tsx:374–385` runs placement loaders before auth selection. Without a stored II session, `loadBackendRouting.ts:70–96` reads Supabase and canister copies, and `loadIcpAdminOverrides.ts:28–34` reads Supabase overrides. Restored II sessions bypass those queries at `loadBackendRouting.ts:65–69` and `loadIcpAdminOverrides.ts:21–26`. This is a current hybrid bootstrap dependency, not confirmed ICP member-data persistence. A strict ICP-only first visit would need a separate on-chain bootstrap path.
- **Missing feature-canister configuration still permits a Supabase provider.** `frontend/src/live/loadBackendRouting.ts:219–222` resolves unavailable features to Supabase; `frontend/src/live/featureRouter.ts:69–80` rescues an II identity only if that feature ID exists, otherwise calls `providers.supabase()`. Correct configured-target tests do not cover a strict no-fallback invariant under missing IDs/session restoration. Preserve fresh-checkout tolerance without sending authenticated ICP data operations to Supabase.

- Payments/IAP verification and phone push delivery remain external by policy. `frontend/src/live/features/messaging.ts:255–257` invokes the external push-kick function; the inspected handler reads/acknowledges ICP queues and sends through FCM, not a demonstrated Supabase message/notification-table copy.

Their app records, settings and authorization should still stay on ICP. Website previews currently use a messaging-canister HTTPS outcall; `/api/fetch-link-preview` is inside the alternate Supabase provider.
- ICP chat recap has a real canister-to-canister LLM path (`useChatCatchUp.ts:243–274`, `messaging_domain/src/main.mo:3499–3520`). It is not a new Supabase inference gap. Full-history/encrypted-transcript recap parity and the LLM service's internals were not independently verified.
- Resend connection remains deferred by the owner. Email jobs can be on-chain while an external provider sends them; activation/receipt checks still matter. Google Drive remains intentionally deferred for ICP.
- Club website registration still needs a Supabase admin session (`websiteBackendSync.ts:40–55`); an ICP routing save explicitly skips it (`PlacementAdminSettingsPage.tsx:470–476`). This is an incomplete external website integration, not a claim that the routing save itself writes Supabase. Its diff also still describes per-club overrides rather than proving country-derived/group-aware synchronization.
- Legacy Supabase media references can still require Storage signing. New ICP ciphertext takes the decrypt branch (`useSignedPhotoUrl.ts:171–174`); no raw-ciphertext fallback was established. Moving encrypted media remains prohibited without new approval.
- Browser/native caches, decryption, local file parsing, ZIP/JSONL assembly and writable download sinks are device operations, not off-chain authoritative records. Whole-service export and historical recovery expansion remain deferred.
- Generic mini-league invite metadata is still rejected at `JoinTeamPage.tsx:1520–1543`, but supported named-player/admin/parent links exist; no current producer of an unsupported generic format was established. Post-acceptance best-effort PII grants also need retry verification; neither is counted as a proven new Supabase dependency.
- The inspected moderation wrappers supply subject kind/ID. The defensive no-subject close in `ReportContentDialog.tsx:90–96` is not evidence that a current normal entry point drops a report; verify readback rather than claiming it does.

## Verification and assurance limits

- Four independent read-only reviews covered clubs/members/auth/rewards/invites, chat/pitch/polls/media/news/Vault, events/competitions/reports/imports, and admin/shared services/workers. Central findings above were checked against current source.
- Static candidate inventory excluding `.test.ts(x)` and `/lab/`: **495 distinct files**, including 2,693 table/RPC sites, 126 function-call sites, 69 Storage sites and 75 realtime sites. These are candidates, not 2,963 ICP leaks; many belong to valid Supabase branches. The scan does not recognize every possible alias/transitive call.
- Existing ICP guard **passed**; all **17 Candid contracts passed drift checks**. The guard checks file-level marker presence, function/Storage calls and Vault table/RPC calls—not full control flow, ordinary table/auth/realtime calls elsewhere, transitive service persistence, complete group coverage or deployed versions. A passing guard therefore did not detect the confirmed findings.
- Existing five-file routing/register/sentinel check: Supabase **36 passed / 22 skipped**, ICP **58 passed**. Separate exception-marker suite: **9 passed**. Source-string sentinel/register tests are not behavioral proof that every feature works or never touches Supabase.
- Reproduced invite/legal checks: **16 passed / 3 failed** across two files. All failures are in `JoinTeamPage.icp.test.tsx` (team token resolution, old mini-league-unavailable expectation, admin-link claim); legal hook tests pass but do not cover the faulty refresh isolation. The invite failures use older mock/expectation paths and do not prove the deployed join flow is broken. They require test reconciliation and real-flow verification, not suppression.
- Latest available preview build log reports **build OK**. No app code was edited or manual build/typecheck run for this audit.
- No signed-in II browser flow, real two-group action, live scheduler/provider execution, module inventory or remote function deployment was verified. No live mutation/deployment occurred. Protected upgrades and matching app release remain prerequisites for unreleased prior changes, separate from the code defects identified here.

## Recommended bounded closure

Close A1–A7 and B1 together with focused no-Supabase behavioral regressions, then C1–C6 with concrete outcome tests. Treat D separately as the ICP bootstrap/no-fallback hardening decision. Preserve external providers, deferred Resend/Drive and unknown-operation locks. Use reviewed exact all-group release scopes only after code and tests pass; do not infer that the new workflow's existence proves runtime release acceptance.
