- pii_access_control is vetKeys IBE: the canister holds NO key material and no decrypt path — writers encrypt client-side to identity `pii_id ++ "\u{1F}" ++ field_id` under the canister's derived public key, readers fetch their vetKey through the can_read/club-grant-gated vetkd relay (all crypto in frontend/src/live/piiVetKeys.ts). State has no initializers and is seeded by the migration chain (bootstrap 20260913_000000, vetKeys migration 20261002_100000) — required by --enhanced-migration.
- PII records are keyed pii_id = entity id, field_id = logical field (e.g. "name"); readers list grants decrypt access, enforced canister-side in can_read — never trust browser-supplied reader grants without a verified relationship.
- PII club-scoped read grants: club_read_grants (pii_id, field_id, club_id) let any principal verified live as club staff via club_domain.has_club_staff_role decrypt the field; grant/revoke via grant_pii_read_club/revoke_pii_read_club (governor or domain owner). events_domain stores no names — Child is { id; parent_id }, and guest/fill-in/MVP names are opaque PII references ("guest:<event>:<uuid>", "fillin:<event>:<uuid>", "mvp:<event>"); legacy plaintext values render as-is client-side.
- Motoko toolchain: moc 1.16.1 via `bun add -g ic-mops && mops toolchain use moc 1.16.1` (binary at /root/.cache/mops/moc/1.16.1/moc; /root is wiped on sandbox resets, reinstall then). Per-canister: `cd backend/<c> && mops install`; compile `moc $(mops sources) --enhanced-migration src/backend/migrations --check src/main.mo`; `--enhanced-migration` takes the migrations DIRECTORY as its argument. .did: same invocation with `--idl src/main.mo` writes main.did in cwd, copy over <c>.did. Bindings: `frontend/node_modules/.bin/icp-bindgen --force --did-file backend/<c>/<c>.did --out-dir` for BOTH frontend/src/lab/bindings/<c> and frontend/src/lab/generated-contracts/<c>. Drift: `node frontend/scripts/check-candid-drift.mjs`.
- Deploy-script rule: Motoko canisters take the governor as an install argument — deploy with `--argument '(principal "<deployer principal>")'` at first install. There is no `initialize()`; first-caller-wins does not exist.
- Deploy-script rule: immediately after install, the deploy script MUST call `pii_access_control.set_club_domain_canister(<club_domain canister id>)` — club-scoped PII read grants never authorize anyone while this is unset (fail-closed by design).
- Deploy-script rule: pii_access_control's `VETKD_KEY_NAME` env var MUST be set to the production key (`key_1`) at first install — the key name is immutable afterwards and a mismatch makes all stored ciphertext undecryptable.
- media_blob_store stores and serves only IBE ciphertext (no crypto, no key material on the canister; http_request is public by design — authorization happens at vetKey derivation on pii_access_control). Its contract in media_blob_store.did is fixed (frontend uploader + migration script pin it) — do not add/change methods without updating that file and the bindings. It has no initialize(): the deploy script MUST set the `GOVERNOR_PRINCIPAL` env var (deployer principal) before first use or delete_blob/abort override rights stay unset (fail-closed).
- Deploy-script rule: immediately after install, the deploy script MUST call `messaging_domain.set_notification_queue_canister(<notification_queue canister id>)` and `notification_queue.set_messaging_domain_canister(<messaging_domain canister id>)` — the chat notify fan-out hook is fail-closed while unset (messages send fine, no chat notifications enqueued), and record_chat_notify_batch only trusts recipient/mute lists from the configured messaging_domain principal (user callers may only fan out their own messages; their mute list is ignored).
- Deploy-script rule: immediately after install, the deploy script MUST call `club_domain.set_notification_queue_canister(<notification_queue canister id>)` and `events_domain.set_notification_queue_canister(<notification_queue canister id>)` and `media_blob_store.set_club_domain_canister(<club_domain canister id>)` — the club-staff blob-delete authorization is fail-closed while unset. The club_domain call also gates the fee-reminder fan-out (send_fee_reminders). Fee reminders reuse the MemberPayment paid-record ledger ("pending" = no paid record for the period/type), not a parallel status schema.
- Deploy-script rule: immediately after install, the deploy script MUST call `club_domain.set_events_domain_canister/set_messaging_domain_canister/set_pii_canister` and `events_domain.set_club_domain_canister` + `messaging_domain.set_club_domain_canister` — permanent club/team deletion (manual or the club_domain 30-day auto-purge timer) fans out to delete_club_data/delete_team_data on events_domain and messaging_domain and purge_club_grants on pii_access_control. Receivers fail-closed on caller == club_domain_canister while unwired; club_domain skips a domain whose id is unset (local purge still completes). pii_access_control's purge only revokes club read grants — PII records stay parent/event-creator-owned, and children/guardian/family records on club_domain are kept for the same reason. The purge timer is a transient initializer (re-arms on upgrade); purge_expired_deletions is also governor-callable for a manual sweep.
- Deploy-script rule: when `ICP_PUSH_WORKER_SEED` (64-hex Ed25519 seed) is set, the deploy script MUST call `notification_queue.grant_worker(<principal derived from the seed>)` — push delivery (scripts/icp-push-deliver.mjs, run by the icp-push-deliver GitHub workflow) is fail-closed while the worker principal is ungranted. Device tokens live ON notification_queue (register_device_token caller-scoped; list_device_tokens/remove_device_tokens worker-gated); recover() resets ALL Processing items to Pending, so only run the worker serialized (workflow concurrency group) — never two workers at once.
- Deploy-script rule: the deploy script SHOULD call `club_domain.set_app_config("backend_routing_config", <JSON mirroring the Supabase app_settings row>)` — `get_app_config` is a public anonymous query used as the routing-config fallback tier when Supabase is unreachable at boot (precedence: Supabase app_settings > build-time env JSON > club_domain app_config > localStorage cache > hardcoded default).
- club_domain exposes a public anonymous `http_request` serving `GET /club?id=<uuid>&scope=<club|subscription|teams|sponsors|all>` as JSON for the club website's server-to-server resolver. Only website-safe fields may be serialized there — never shell-team contact name/email, PlayHQ link ids, principal fields, or any other internal/PII field.
- Migration files are immutable once any deploy may have run them: mainnet records applied migrations by name and skips them, so edits to an applied file never execute and later steps trap on missing fields. Add new state via a NEW, later-timestamped migration (partial `func migration(_ : {}) : { var x : T }` is fine).
- events_domain scheduled RSVP reminders live in `autoReminders` (set via set_event_auto_reminder) and are swept by a transient 15-minute recurring timer that reuses send_event_reminders' fan-out; series cancel is the atomic set_series_cancelled (from_ms onward). Both need notification_queue wired for delivery. Recurring creates from the browser pass exact dates: create_series with until = first start, then add_series_occurrence per date — never rely on frequencyStepMs for weekday/monthly patterns.
- Deploy-script rule: immediately after install, the deploy script MUST call `vault_domain.set_club_domain_canister(<club_domain canister id>)` — vault writes accept any principal holding a role in the club on club_domain (has_club_staff_role) in addition to local vault grants; fail-closed while unset.
- Batched read queries (club_domain get_club_profiles/get_teams/list_teams_multi/get_*_subscriptions/list_sponsors_multi; events_domain list_events_multi/get_event_rosters/list_duties_multi; messaging_domain get_mute_preferences/get_group_metadata_multi/list_groups_by_clubs; mini_league_domain get_mini_leagues/list_mini_leagues_by_clubs) back the same-tick coalescer in frontend live/features/batching.ts — callers keep single-id helpers; it falls back per method on older canisters. Batch queries must apply the same visibility check as their single-id twin. Why: per-id fan-out dominated ICP page-open time.
- Photo-store sharding: extra stores are separate media_blob_store canisters registered under keys media_blob_store_2, _3, … (same source, own canister.yaml/icp.yaml entry, GOVERNOR_PRINCIPAL set; the deploy script wires every media_blob_store_N to club_domain). Stores are append-only and photos are never rebalanced — each photo's blob_ref/URL names its store. A store refuses begin_upload with "StoreFull" past 80% of capacity_limit_bytes (governor set_capacity_limit; at/below total = read-only) and stays readable; the frontend picks a store per club by rendezvous hash and falls through to the next on StoreFull.
- Per-club photo lock: pii_access_control.get_club_media_vetkey(club_id, transport) derives the vetKey for identity `clubmedia:<club_id>` U+001F `blob`, authorized live by club_domain.is_club_member (or governor); no stored record. club_media_lock_version() is the capability probe. Why: one paid derivation per member per club per session instead of one per photo.
- events_domain mirrors club/team admin and coach roles from club_domain.list_user_club_roles on create_event/create_series/create_recurring_series/update_event/create_team_training_pause (replacing the caller's mirror for that club) — club_domain is the source of truth for roles; needs events_domain.set_club_domain_canister wired.
- Deploy-script rule: immediately after install, the deploy script MUST call `competition_domain.set_club_domain_canister(<club_domain canister id>)` — competition management mirrors the caller's live club_admin grant from club_domain (fail-closed while unset). Competition broadcasts are logged on competition_domain; push fan-out to entered teams' members is done client-side through notification_queue.fan_out.
