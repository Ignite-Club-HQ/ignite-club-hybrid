- pii_access_control is vetKeys IBE: the canister holds NO key material and no decrypt path — writers encrypt client-side to identity `pii_id ++ "\u{1F}" ++ field_id` under the canister's derived public key, readers fetch their vetKey through the can_read/club-grant-gated vetkd relay (all crypto in frontend/src/live/piiVetKeys.ts). State has no initializers and is seeded by the migration chain (bootstrap 20260913_000000, vetKeys migration 20261002_100000) — required by --enhanced-migration.
- PII records are keyed pii_id = entity id, field_id = logical field (e.g. "name"); readers list grants decrypt access, enforced canister-side in can_read — never trust browser-supplied reader grants without a verified relationship.
- PII club-scoped read grants: club_read_grants (pii_id, field_id, club_id) let any principal verified live as club staff via club_domain.has_club_staff_role decrypt the field; grant/revoke via grant_pii_read_club/revoke_pii_read_club (governor or domain owner). events_domain stores no names — Child is { id; parent_id }, and guest/fill-in/MVP names are opaque PII references ("guest:<event>:<uuid>", "fillin:<event>:<uuid>", "mvp:<event>"); legacy plaintext values render as-is client-side.
- Motoko toolchain: moc 1.16.1 via `bun add -g ic-mops && mops toolchain use moc 1.16.1` (binary at /root/.cache/mops/moc/1.16.1/moc; /root is wiped on sandbox resets, reinstall then). Per-canister: `cd backend/<c> && mops install`; compile `moc $(mops sources) --enhanced-migration src/backend/migrations --check src/main.mo`; `--enhanced-migration` takes the migrations DIRECTORY as its argument. .did: same invocation with `--idl src/main.mo` writes main.did in cwd, copy over <c>.did. Bindings: `frontend/node_modules/.bin/icp-bindgen --force --did-file backend/<c>/<c>.did --out-dir` for BOTH frontend/src/lab/bindings/<c> and frontend/src/lab/generated-contracts/<c>. Drift: `node frontend/scripts/check-candid-drift.mjs`.
- Deploy-script rule: Motoko canisters take the governor as an install argument — deploy with `--argument '(principal "<deployer principal>")'` at first install. There is no `initialize()`; first-caller-wins does not exist.
- Deploy-script rule: immediately after install, the deploy script MUST call `pii_access_control.set_club_domain_canister(<club_domain canister id>)` — club-scoped PII read grants never authorize anyone while this is unset (fail-closed by design).
- Deploy-script rule: pii_access_control's `VETKD_KEY_NAME` env var MUST be set to the production key (`key_1`) at first install — the key name is immutable afterwards and a mismatch makes all stored ciphertext undecryptable.
- media_blob_store stores and serves only IBE ciphertext (no crypto, no key material on the canister; http_request is public by design — authorization happens at vetKey derivation on pii_access_control). Its contract in media_blob_store.did is fixed (frontend uploader + migration script pin it) — do not add/change methods without updating that file and the bindings. It has no initialize(): the deploy script MUST set the `GOVERNOR_PRINCIPAL` env var (deployer principal) before first use or delete_blob/abort override rights stay unset (fail-closed).
- Deploy-script rule: immediately after `initialize()`, the deploy script MUST call `messaging_domain.set_notification_queue_canister(<notification_queue canister id>)` and `notification_queue.set_messaging_domain_canister(<messaging_domain canister id>)` — the chat notify fan-out hook is fail-closed while unset (messages send fine, no chat notifications enqueued), and record_chat_notify_batch only trusts recipient/mute lists from the configured messaging_domain principal (user callers may only fan out their own messages; their mute list is ignored).
- Deploy-script rule: immediately after `initialize()`, the deploy script MUST call `club_domain.set_notification_queue_canister(<notification_queue canister id>)` — the fee-reminder fan-out (send_fee_reminders) is fail-closed while unset. Fee reminders reuse the MemberPayment paid-record ledger ("pending" = no paid record for the period/type), not a parallel status schema.
- Deploy-script rule: the deploy script SHOULD call `club_domain.set_app_config("backend_routing_config", <JSON mirroring the Supabase app_settings row>)` — `get_app_config` is a public anonymous query used as the routing-config fallback tier when Supabase is unreachable at boot (precedence: Supabase app_settings > build-time env JSON > club_domain app_config > localStorage cache > hardcoded default).
